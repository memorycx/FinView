# common/GlobalExceptionHandler.java文件阅读

@RestControllerAdvice 的作用

```

请求 → DispatcherServlet → Controller  
↓ (Controller 抛异常)  
异常沿着调用栈向上冒泡  
↓  
Spring AOP 捕获到异常  
↓  
扫描所有 @RestControllerAdvice 类  
↓  
找到 @ExceptionHandler 匹配的方法 → 执行  


```

  ```
  
  Controller 执行业务逻辑  
│  
├─ 正常 → return Result.success(data)   前端收到 {code: 0, message: "", data: ...}  
│  
└─ 异常  
│  
├─ throw new BusinessException(404, "用户不存在")  
│      │  
│      ▼ GlobalExceptionHandler.handleBusiness()  
│             ├─ log.warn("业务异常 code=404, message=用户不存在")  
│             └─ return Result.error(404, "用户不存在")  
│                        → 前端收到 {code: 404, message: "用户不存在", data: null}  
│  
└─ 其他 RuntimeException / Error  
│  
▼ GlobalExceptionHandler.handleException()  
├─ log.error("服务端内部错误", ex)  ← 这里会打印完整堆栈  
└─ return Result.error(500, "服务端内部错误")  
→ 前端收到 {code: 500, message: "服务端内部错误", data: null}  
  
@RestControllerAdvice 让 Spring 知道"这是个全局异常处理器"，@ExceptionHandler 定义了"每种异常对应怎么处理"，Lombok 的 @Slf4j 只是帮你省了 Logger 的声明。三者组合起来，实现了异常处理的 集中化 + 声明式。


  ```





本项目的异常处理为三层职责分离：

1. Controller：收参数 → 调 Service → 返回结果（只管正常流程）
2. Service：业务逻辑校验，发现异常直接 throw
3. GlobalExceptionHandler：兜底接住所有异常，统一包装返回


```

SavingsController.getPlan(id)  
│  直接调用 service，没做 try-catch  
▼  
SavingsService.getPlan(id)          ← 真正 throw 的地方  
│  
├─ savingsMapper.selectPlanById(id) 返回 null  
│  throw BusinessException.notFound("存钱计划不存在: 123")  
│  
▼  异常冒泡（Spring AOP 拦截）  
GlobalExceptionHandler.handleBusiness()   ← 接住、打日志、包装返回  
│  
▼  
前端收到 HTTP 200 + {code: 404, message: "存钱计划不存在: 123", data: null}  


```




# 日志配置

**日志配置**  
在 resources 目录下创建 logback-spring.xml 文件

appender 管道  定义"日志往哪里写、用什么格式写"  
logger   阀门     定义"哪个包的什么级别要放行"  
root     总水闸    所有 logger 的父级，没单独配置的都走它

**错误排查**  
缺堆栈，没法排查  
log.error("出错了: {}", ex.getMessage());

完整堆栈,可以排查  
log.error("出错了", ex);

**高并发**  
高并发场景下，写一个拦截器，在请求入口塞入 traceId

# DTO


数据库        Entity        DTO          Controller        前端  
(user 表)  (持久层对象)   (传输层对象)        (Web 层)      (HTTP 消息)


```

前端发来 JSON {"username":"xxx","password":"xxx"}  
│  
▼  
LoginRequest DTO（带校验注解的接收对象）  
│  
▼ Controller 里转换  
User Entity（和数据库打交道）  
│  
▼ Service 里转换  
LoginResponse DTO（脱敏后的返回对象）  
│  
▼  
前端收到 JSON {"token":"xxx","userId":1,"username":"xxx",...}  


```


Entity 是 数据库的镜子，DTO 是 前后端的合同。它们的字段、注解、职责都不一样，不能混用。单独建 dto 文件夹就是为了把"数据库对象"和"HTTP 消息对象"隔离开，既避免敏感数据泄露，又让每层的职责清晰。



```

SpringApplication.run(FinViewApplication.class, args)  
│  
├─ 创建 ApplicationContext  
├─ 实例化并注入所有 Bean（包括 DataInitializer、UserMapper、PasswordEncoder）  
├─ 执行 schema.sql 建表  
├─ 执行 data.sql 清表  
├─ 遍历所有 ApplicationRunner Bean ← 找到 DataInitializer  
│   └─ 调 run(ApplicationArguments args)  
│       ├─ seed("admin", ...)   ← 查库，已存在？跳过；不存在？插入  
│       └─ seed("demo", ...)    ← 同上  
├─ 启动 Tomcat，监听 8080  
└─ main() 返回，应用就绪 🎉  


```

总结：DataInitializer.run() 是 Spring Boot 启动时的"最后一公里钩子"——你在这里做数据库种子数据、缓存预热、第三方 SDK 初始化等需要等所有基础设施就绪之后才能做的事。

数据库是如何被初始化的？

**依赖层**

```
<dependency>  
    <groupId>org.mybatis.spring.boot</groupId>  
    <artifactId>mybatis-spring-boot-starter</artifactId>  
</dependency>  
<dependency>  
    <groupId>com.mysql</groupId>  
    <artifactId>mysql-connector-j</artifactId>  
</dependency>  
  
mybatis-spring-boot-starter → 传递依赖了 spring-boot-starter-jdbc → 里面有 spring-jdbc → 提供了 DataSource 自动配置 + SQL 初始化能力。  

```

在 application.yml 中配置数据库**初始化**：


```
sql:  
    init:  
    # 启动时自动建表（IF NOT EXISTS）并写入种子数据（INSERT IGNORE，可重复执行）  
    mode: always  
    schema-locations: classpath:db/schema.sql  
    data-locations: classpath:db/data.sql  
    encoding: UTF-8  
    
```


SQL 文件本身不会自己跑，是 Spring Boot 的 JDBC 自动配置 (DataSourceInitializationConfiguration) 在数据源就绪之后，根据你 yml 里写的 spring.sql.init.* 配置，用 JdbcTemplate 帮你逐条执行的。 mode: always 让它在 MySQL 这种非内存数据库上也能跑，IF NOT EXISTS / DROP TABLE IF EXISTS 保证它能安全地重复执行。
